# Little Railways V1.1 — proposed implementation design

Status: proposed for user review; no gameplay code changed yet.

## Intent and constraints

Implement the supplied V1.1 brief as an incremental change to the existing Next.js/React/TypeScript/Canvas game. Preserve branding, typography, colours, grass/scenery, train artwork and smoke, sounds, driving controls, camera, history and saving. Add no unrelated features or dependencies. Keep one active locomotive.

The inspected GitHub `main` head is `6deeea02a0872b587cdc796248f1d11c366c6302`, matching the existing local source tree before this design. The existing game has 49 unit tests. Vercel is already connected to this GitHub repository; this design does not change the live deployment.

## Inspection findings and change surface

- `types.ts` fixes endpoint IDs at 0/1 and stores train distance on a piece without a path ID.
- `geometry.ts` returns one endpoint pair and one straight/quarter-circle path per piece.
- `network.ts` treats piece IDs as graph nodes and assumes both ends determine a unique route. A crossing cannot be represented safely by merely adding four endpoints to this model.
- `simulation.ts` follows actual geometry and external links with preserved overshoot. Retain that integration and acceleration algorithm, extending its current path identity and entry resolution.
- `editor.ts`, board hit detection and grid placement assume a one-cell footprint.
- `rendering.ts` and `TrackPreview.tsx` draw one path per piece.
- `RailwayGame.tsx` starts from `sampleLayout()` plus `defaultStart`; autosaving can write that demonstration without a construction action.
- Existing save validation and the two release-review fixes must remain intact: invalid restored train starts are cleared, and corrupt startup/manual loads suspend autosaving.

Change these existing modules in place. Add small pure route/footprint/occupancy helpers where needed. Keep rendering and React independent of deterministic railway logic.

## Chosen geometry and alternatives

Recommended: a one-cell crossing and two-cell left/right switches. This reuses the current quarter-circle geometry and provides a visible shared approach before divergence.

A one-cell switch using an immediately diverging quarter-circle is mathematically possible, but crowds the points and frog at the cell boundary. A larger sweeping turnout would require longer/custom curves and a larger footprint. The two-cell design is the smallest recommended practical turnout for the existing track scale.

Base orientation is west-to-east. Rotate complete geometry and footprint through the existing quarter-turn transform about the anchor cell centre.

| Piece | Physical ports in local world units | Paths |
| --- | --- | --- |
| Straight | West `(0,.5)`, east `(1,.5)` | Existing unchanged path |
| Curve | West `(0,.5)`, south `(.5,1)` | Existing unchanged arc |
| Crossing | West `(0,.5)`, east `(1,.5)`, north `(.5,0)`, south `(.5,1)` | West/east and north/south, independent |
| Left switch | Common `(0,.5)`, straight `(2,.5)`, branch `(1.5,0)` | Length-2 straight; length-1 approach then radius-.5 quarter-circle turning north |
| Right switch | Common `(0,.5)`, straight `(2,.5)`, branch `(1.5,1)` | Length-2 straight; length-1 approach then radius-.5 quarter-circle turning south |

Switch footprints occupy anchor cell `(0,0)` and second cell `(1,0)` before rotation. Their branch paths have length `1 + π/4`. All external tangents match neighbouring straight/curve rails. The branch geometry is a true circular arc after the shared approach, not a diagonal. Position and tangent are continuous at the approach/arc join and piece boundaries.

## Ports, paths and graph

Extend Track type with `crossing`, `switch-left` and `switch-right`, and switch state `straight | branch`. Each definition exposes all physical ports plus separately identified traversal paths. Each path defines its two port IDs, length and pose sampler.

Use stable path IDs, with the legacy single path defaulting to `main`. Crossings have `main` and `cross`; switches have `main` and `branch`. Train state and saved starting position identify both piece and path. Missing legacy path IDs resolve to `main` only for legacy straight/curve pieces.

Keep external endpoint matching by position and opposing tangents. Distinguish physical connections from active traversal:

1. Match physical ports, including an inactive turnout outlet, so placement/snapping can recognise actual rails.
2. Expose both independent crossing paths and only the selected switch path to active routing.
3. Build connected components and loops from piece-plus-path nodes. The two paths within a crossing never connect through their shared centre.
4. When entering a piece, resolve the active path incident to that entry port. If none exists, stop at the preceding track’s endpoint; do not enter the inactive branch.
5. Derive loop length from path lengths, so a physical crossing tile may belong to two distinct circuits without false connectivity or incorrect lap distance.

Update the graph only when tracks or switch state change. Resolve the next route at each endpoint using the latest graph; do not precompute a stale full circuit.

## Movement and occupancy

Preserve delta-time acceleration, overshoot consumption, pause/stop/reverse and tangent-based train drawing. Sample the selected path throughout movement, including the two-part switch branch. Carry path identity across transitions in both directions.

A crossing always sends a train to the opposite port. A switch allows common-to-selected-outlet and selected-outlet-to-common travel. Entering the inactive outlet stops safely before the turnout.

Switch toggling uses live `trainRef.current`, not the throttled UI telemetry. Block changes when the locomotive occupies the switch, including its front/rear overhang. Use a deterministic geometric occupancy helper against the rotated switch footprint with conservative clearance. Report “Wait until the train has passed!” or disable the route buttons.

Changing a switch while the train is elsewhere must preserve the train’s current position, path, direction and speed. Rebuild active routing for future entry. Reset lap accounting when the active topology changes. If the saved reset position is on that switch’s now-inactive path, update that reset position to the active path midpoint; the currently travelling train does not move. Revalidate starting positions after construction changes, history changes and loads.

## Editing and interaction

Extend placement validation to every occupied cell in a rotated footprint. Reject outside-board, overlap and invalid rotation atomically without committing history. Keep existing one-cell straight/curve placement unchanged.

Use a shared footprint-aware hit helper for selection, train placement and keyboard grid selection. Selecting either cell of a switch selects the entire piece. Moving a switch preserves the pointer’s grab offset so picking its second cell does not jump the piece. Rotation and removal operate on the whole piece. Preserve switch state through movement, rotation, undo and redo.

Retain the current track cards and add Crossing, Left Switch and Right Switch using the same Canvas miniature style. Make only the track-card strip horizontally scrollable when needed; keep Select, Rotate, Pan and Remove accessible. Preserve existing control typography, colours and overall page structure.

Selecting a switch exposes labelled Straight/Branch route buttons with an active state. Allow an unmoved tap on a switch in Drive mode to select its route control while a drag still pans. All other construction remains locked in Drive mode. The route control is keyboard-accessible and reachable on phones.

Train placement chooses a valid active path nearest the tapped rail; the crossing’s two paths remain selectable. Extend the existing grid-placement form with a route choice when needed for keyboard placement on a crossing. Do not place a train on an inactive switch path.

## Empty first launch and safe save migration

Initial React state contains `[]` tracks and no locomotive. Keep all existing terrain and scenery. Show exactly:

> Let’s build your railway! Choose a track to get started.

Selecting or placing an engine when there are no tracks shows:

> Build some track before adding your train!

Play without a valid train explains that the player must choose an engine and place it on track. Neither action creates tracks. Open routes remain usable and stop safely at their ends.

Keep New as the existing confirmed empty-board action. Retain the existing explicitly selected sample-layout control; it is never invoked automatically.

Write save schema version 2 with path IDs, new piece types, switch state and provenance metadata. Keep reading the existing LocalStorage key so V1 saves are found. Validate and migrate V1 straight/curve layouts in memory without losing positions, rotations, train choice/start or mute. Persist upgraded data through the normal validated saving flow. Reject invalid footprints, path references and switch state before applying a load.

Important compatibility limitation: existing V1 saves have no provenance marker. An untouched demonstration saved automatically is indistinguishable from a player deliberately saving the identical starter layout. Preserve every unmarked valid V1 save. Do not infer permission to erase it from matching the sample’s IDs or shape. New provenance can identify explicitly marked automatic demo records, but this update no longer produces automatic demos. Any known, explicitly marked automatic demo may initialise an empty board while retaining the original record until an explicit user save/recovery action. Corrupt records continue to be preserved with autosave suspended.

## Verification

Retain all existing geometry, simulation, history and persistence tests; update browser tests that deliberately relied on automatic sample initialisation to load the sample explicitly.

Add unit tests for:

- Crossing ports, both independent paths, every rotation and all four traversal directions; no perpendicular transition or false component/loop merge.
- Both turnout geometries, shared approach/arc tangent continuity, all rotations and neighbours aligned at every outlet.
- Active path changes, inactive-entry stopping and aligned reverse traversal from either outlet.
- Multi-cell bounds, overlap, selection, movement/rotation state preservation and history.
- Occupancy locks including nose/tail overhang and allowed switching with the train elsewhere.
- V1 migration, V2 switch/path round trips, invalid saves, preserved damaged records and reset-position revalidation.
- Legacy oval laps, open-end stops, disconnected rails, distance conservation and frame-rate independence.

Add desktop and phone browser checks for:

1. First launch has zero pieces and no train, with exact introductory message.
2. Empty-board engine selection and Play create no tracks and show guidance.
3. Existing saves load unchanged; New creates an empty board.
4. All five cards place/rotate/remove/undo; multi-cell invalid placements are rejected.
5. A user-built crossing passes trains straight along each route.
6. Both switches can be selected and changed; moving trains follow the chosen branch; occupied switching is blocked.
7. Saving/refreshing retains the railway, chosen crossing path and switch alignments.
8. Existing transport controls, camera, sample flow and mobile quick controls still work.

Run Vitest, TypeScript, production build and Playwright. Compare screenshots against the existing layout and artwork; only new piece previews, scrolling and the switch route control should change. Report physical-device limits explicitly. Do not declare V1.1 complete until acceptance passes or specific unavailable checks are identified.

## Delivery boundary

Implement and test on a feature branch. Preserve the live V1 deployment during development. Publishing a V1.1 production deployment is separate from this implementation and verification work.
