# Little Railways V1.1 Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` for the previously selected inline execution method. Work task by task, with regression tests and one final independent review. Track steps below.

**Goal:** Start new players on an empty board and add independent crossings plus functional, safely controlled left/right switches without replacing the current application.

**Architecture:** Extend the existing geometry/graph/simulation modules from one path per tile to separately identified paths and physical ports. Retain React controls, Canvas rendering/caching, delta-time integration, history, LocalStorage and the visual design. Add footprint and switch safety helpers, keeping railway logic pure.

**Tech Stack:** Existing Next.js, React, TypeScript, Tailwind, Canvas 2D, Vitest and Playwright; no new dependencies.

**Spec:** [Approved V1.1 design](../specs/2026-10-21-v1.1-track-routing-design.md).

## Global Constraints

- Preserve branding, typography, colours, grass/scenery, train artwork and smoke, sounds, driving controls, camera, history and saving.
- Add no unrelated features or dependencies. Keep one active locomotive.
- Crossing paths do not connect at their shared centre.
- Switches occupy two cells and use a true quarter-circle branch after a shared straight approach.
- Retain all unmarked valid V1 saves, including those identical to the demonstration; no retrospective provenance is available.
- Preserve corrupt saved records with autosave suspended until an explicit recovery action.
- Implement on `feature/v1.1-track-routing`. Preserve live V1 production during development; publishing V1.1 production is outside this plan.

## Review Focus

- Picking up the second cell of a switch must preserve its grab offset and state; outside drops must not modify history.
- A train’s nose/tail may occupy a switch while its centre belongs to another track; toggling must remain blocked.
- Changing alignment ahead of a moving train must affect its next entry without moving its current pose or changing speed.
- Undo after loading a reused piece ID with different paths/lengths must clear an invalid train start and keep saves valid.
- Two separate loops sharing a crossing must remain separate circuits with independent path-based lap lengths.

## Files and interfaces

Modify the existing `lib/railway/{types,geometry,network,simulation,editor,persistence}.ts` modules. Add `lib/railway/footprints.ts`, `switches.ts` and `startup.ts` for pure helpers. Update existing `RailwayGame`, `RailwayBoard`, `BuildingBox`, `TrackPreview`, rendering and CSS in place. Add `tests/v1.1-*.test.ts` and `e2e/v1.1.spec.ts`; adjust existing tests only where their assumptions intentionally change. Update README and AGENTS after acceptance.

Shared types:

- `TrackType = 'straight' | 'curve' | 'crossing' | 'switch-left' | 'switch-right'`.
- `PathId = 'main' | 'cross' | 'branch'`; `PortId = 0 | 1 | 2 | 3`; `SwitchState = 'straight' | 'branch'`.
- Extend Track with the new type union and optional `switchState`, required and validated for switch pieces in V2 saves.
- `TraversalPath = { id: PathId; ports: readonly [PortId, PortId] }`; a path’s side is still `0 | 1`, distinct from physical port IDs.
- `StartPosition.pathId?: PathId` preserves legacy constructor calls. `createTrain` normalizes it to `main`; decoded V2 starting positions always include a validated path ID.
- `SavedLayout` is normalized version 2 with `source: 'user' | 'auto-demo'`. V1 is an input schema accepted by `decodeSave`, not an output schema written by the new game.
